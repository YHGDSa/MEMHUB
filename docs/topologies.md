# 部署拓扑：一台机器也能有“上游”

> 结论先说：**上游不是“第二台电脑”，而是四个 HTTP 端点。** 虚拟机、云主机、甚至同机的一个进程都能当上游；多机协作的真正前提是“有一个所有机器都能到达的被动副本”，不是“买第二台机器”。

## 1. 三种拓扑

| 拓扑 | 谁跑 hub | 谁写 | 离线能写吗 | 适用 |
|---|---|---|---|---|
| **A. 每台机器各跑 hub + 一个共享上游** | 每台本机 | 各自本机 | **能** | 日常多机；网络环境不一致（一台走代理、一台直连） |
| **B. 只在上游跑 hub，其他机器连隧道** | 上游一台 | 都写上游 | **不能**（断隧道即不可写） | 单人单机、想要绝对单一真源 |
| **C. 单机 + 虚拟机当上游** | 本机 + VM | 只写本机 | 能 | 验证/演示多机语义；不想再买一台机器 |

> 这个仓库的默认叙事是 A：每台机器的 hub 是写点，上游是副本。B 会直接把 local-first 退化成普通远程服务。

## 2. A 拓扑的最小上游

上游只需要实现四个端点（`test/smoke.mjs` 与 `test/multi-hub.mjs` 里的 `startStub` 就是参考实现）：

| 端点 | 作用 |
|---|---|
| `GET /agentmemory/livez` | 探活 |
| `GET /agentmemory/export` | 全量导出（对账也靠它） |
| `POST /agentmemory/remember` | 接收写入（含墓碑记录） |
| `POST /agentmemory/forget` | 按 id 删除 |

三种落地方式，成本从低到高：

1. **直接跑本仓库的 hub 当上游**：把它的 `upstream` 配成一个不可达地址（它会一直 offline、不再对外推），它本身就是合规上游。
2. **写一个 40 行的 stub**：照抄 `test/smoke.mjs` 的 `startStub`，加上持久化即可。
3. **用官方 AgentMemory 服务**：如果它在你的目标平台能跑起来（Windows 上目前有两个已知缺陷）。

## 3. 网络怎么搭

| 场景 | 做法 | 注意 |
|---|---|---|
| 本机 + VirtualBox/Hyper-V | Host-only 或 NAT 固定 IP，VM 内 `node src/hub.mjs`，各机器 `ssh -N -L 3112:127.0.0.1:3111 user@vm` | 别把 3111 绑到 0.0.0.0 以外的可达地址 |
| 云主机 | 最小规格即可；**Tailscale/WireGuard** 或 SSH 隧道 | 3111 永远不要公网暴露：只有一把共享 Bearer key |
| 一台机器走代理、一台直连 | 每台机器各跑 hub，本机调用只走 loopback；只有同步这一段跨网络 | `src/mem.mjs` 与看门狗会清空 proxy 变量，避免 loopback 被代理截走 |

SSH 隧道走 22 被拦时，可以改用 `ssh.github.com:443`；隧道用 `keepalive` 自动重连（见 `tunnel.example.cmd`）。

## 4. 这套实现的边界（实测量过）

`test/multi-hub.mjs` 用两个独立 hub + 一个 stub 上游跑了 19 条断言，覆盖：

| 能力 | 结果 |
|---|---|
| A 写、B 读（单向复制） | 通过 |
| 双向复制（B 写、A 读） | 通过 |
| 两台机器各自记录同一条事实 | 默认会上游两份；`POST /hub/reconcile` 按内容 id 收敛为一份 |
| 修订传播（同一逻辑记忆的新版本） | 通过：按 entity id 做 last-write-wins；旧版本由对账清掉 |
| 删除传播 | 通过：删除写墓碑，另一台同步后删除本地副本 |
| 删除后的复活 | 被挡住：墓碑 TTL 内重写同一内容返回 409 |
| 上游丢了某条记录 | 对账发现并重推（self-heal） |

**仍然不支持的**（写清楚，避免误用）：

- 并发编辑同一条记忆（两个版本同时写）按 `updated_at` 取舍，**不是**合并；LWW 会丢一侧。
- 墓碑按“内容哈希”标记，不按“实体”标记：删掉 v2 之后，另一个墓碑未覆盖的旧版本仍可能存在；TTL 过后同一内容可被重新记录（这是有意的）。
- 墓碑会随上游 export 增长；对账会压缩过期的（默认 TTL 30 天，`tombstoneTtlDays` 可配）。
- 鉴权仍是单一 Bearer token：任何能连上游的机器都能写。
- 内容 id 基于归一化后的正文；同一事实换个说法写不会被识别为重复。

## 5. 什么时候该用对账

增量同步是“看到什么学什么”，对账是“拿全集比一次”。触发点建议：

- 两台机器都离线了几天，各自攒了一批写入；
- 怀疑上游被手工改动（导入、清理）；
- 删除了重要记忆，需要确认其它副本也消失；
- 日常可以每天一次定时对账（本仓库没内置定时器，`POST /hub/reconcile` 由外部调度）。

```bash
curl -X POST -H "Authorization: Bearer $S" http://127.0.0.1:3111/hub/reconcile
# {"dupsRemoved":1,"versionsRemoved":1,"repushed":0,"tombstonesCompacted":0,...}
```
