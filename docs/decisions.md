# 设计决策（ADR）

每条记录：背景 / 决策 / 后果 / 放弃的备选。**没有测量的收益一律不写。**

## ADR-001 写入判据改成「本地成功」

- **背景**：上游经隧道访问，断线是常态而非异常；原客户端把写入成功绑定在远端响应上，一次隧道抖动就丢一条记忆。
- **决策**：本地 SQLite 提交成功即返回 200；远端写入降级为 outbox 的异步重放。
- **后果**：断网可写可搜；代价是“本地已有、远端尚无”的窗口，需要 `pendingWrites` 作为可见信号。
- **备选**：写失败即返回 5xx 让调用方重试——把可靠性推给每个调用方，且调用方无法区分“网络抖动”和“真的失败”。

## ADR-002 幂等键用 `upstream_id` 而非内容哈希

- **背景**：补推后拉取会把同一条记录按上游 id 再插一遍，形成两行相同内容。
- **决策**：推送成功即把上游 id 回填到本地行；拉取时若命中本地某行的 `upstream_id` 就跳过。
- **后果**：去重与“内容是否被脱敏改写”解耦；代价是本地行必须持久保存这个映射。
- **备选**：按内容哈希去重——脱敏会改写正文，哈希随之变化，去重失效。

## ADR-003 冲突用 LWW，不宣称共识

- **背景**：两台设备可能先后更新同一条记忆。
- **决策**：`updated_at` 更大的版本覆盖（`WHERE excluded.updated_at >= memories.updated_at`）。
- **后果**：实现简单、可预测；**明确不是**分布式共识，同 id 并发写不在支持范围。
- **备选**：向量时钟/CRDT——在这个使用规模下复杂度与收益不成比例。

## ADR-004 单写者，而不是给多进程加锁

- **背景**：曾在 hub 运行时用第二个进程直接开库，WAL 收尾 checkpoint 折掉正在追加的尾部，丢过 6 条数据。
- **决策**：单写者。读走 HTTP；需要收拢 WAL 时先停服再 `PRAGMA wal_checkpoint(TRUNCATE)`。
- **后果**：少一条并发路径，多一条运维约束（写进 README 与故障表）。
- **备选**：加文件锁/换 Postgres——前者只是把问题挪到锁超时，后者与“零依赖单机工具”的定位冲突。

## ADR-005 `private` 不写 outbox，而不是在推送时过滤

- **背景**：跨 Agent 共享时，某些记忆只应留在本机。
- **决策**：作用域在写入时决定是否入队；`private` 永不产生 outbox 行。
- **后果**：“忘记过滤”这条失败路径在结构上不存在；代价是 `private` 记录同样进本地备份（备份是本机磁盘，不外传）。
- **备选**：统一入队、推送前按 scope 过滤——任何一处漏判就会上浮。

## ADR-006 脱敏在写入路径，不在读取路径

- **背景**：记忆正文里粘进过 token、私钥、带口令的 URL。
- **决策**：落库前替换为 `[REDACTED]` 并返回命中数；读取路径不再处理。
- **后果**：脏数据不入库，快照与备份天然干净；代价是不可逆（原文不保留），偶尔误伤可读性。
- **备选**：读取时脱敏——库里仍有原文，一次导出就泄漏。

## ADR-007 技能目录是唯一写者

- **背景**：技能既能在数据库里写、又能在磁盘目录里放，两处都能写必然漂移。
- **决策**：磁盘 `<skills>/<name>/SKILL.md` 是唯一真源；`skills` 表只是启动/手动 reindex 重建的检索索引；HTTP 写技能返回 409。
- **后果**：跨机同步靠 Git 传输而不引入第二个写者；代价是新增技能要触发 reindex。
- **备选**：DB 主写、目录导出——两个真源，漂移只是时间问题。

## ADR-008 检索不上向量

- **背景**：单机规模几十条记忆、中文子串查询为主。
- **决策**：LIKE + 权重 + 时间衰减，零依赖。
- **后果**：无 embedding 服务、无索引重建、无新失败路径；代价是语义检索能力缺失，规模上去要换 FTS5/向量。
- **备选**：引向量库——在几十条数据上换不来可测收益，却新增一条依赖与一条失败路径。

## 未做但被讨论过的

| 想法 | 为什么没做 |
|---|---|
| 一键安装 exe | 个人工具没有分发需求；引入签名、更新、杀软误报、原生依赖打包，且与“零依赖 + recall is an action”冲突。真要做应是 installer + 托盘。 |
| 图索引 / 上下文压缩 | 先把“写不丢、删得掉、不上浮”做对，再谈更强的检索形态。 |
| 多租户与配额 | 单用户双设备，没有第二个使用者，做了也无法验证。 |
